# Tasks: i18n completo del dashboard (ES/EN) con next-intl

Convenciones de este archivo:

- **Cada fase = un batch** (una sesión enfocada de sub-agente de `sdd-apply`). El orden reproduce Decision 4 del design (backend primero, infra, luego módulos de UI, landing/invite al FINAL) — NO adelantar tareas de una fase posterior.
- **Cada fase deja la app 100% funcional y deployable** (Decision 9): los strings aún no migrados siguen en español hardcodeado y conviven con next-intl sin conflicto. Revertir una fase = revertir sus commits, nada más. La convivencia del patrón viejo (landing/invite con diccionarios caseros) dura hasta la Fase 7 inclusive.
- **AC** = criterio de aceptación, referenciando los escenarios de `specs/dashboard-ui/spec.md`, `specs/account-settings/spec.md` y `specs/auth/spec.md` de este change.
- **Regla de paridad transversal**: toda clave nueva se agrega a `messages/es.json` Y `messages/en.json` EN LA MISMA TAREA que la consume — el test de paridad (2.4) corre verde al cierre de CADA fase, nunca hay EN "pendiente".
- **Precondición dura** (proposal → Dependencies): mergear `feat/email-invitations` ANTES de arrancar la Fase 1 (comparte `InvitationsPanel`, `/invite`, emails, middleware).
- **Versión npm pinneada**: `next-intl@4.13.6` exacta, sin caret (verificada contra el registry el 2026-08-12 — Decision 1). Instalar con `npm install --save-exact`.
- **Gates**: frontend = `npx tsc --noEmit` + `vitest run` (NUNCA `npm run build` — regla del usuario); backend = `pytest` + `black` + `ruff` + `mypy`. Tests de API contra la base real — TimescaleDB local en puerto **5433, NO 5432** (memoria del proyecto).
